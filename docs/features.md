# Feature Reference

What the product does today, and where each feature lives in the code. It replaces the original planning spec (`development_specs/feature-spec-social-media-management-v2.md`, now only in git history). Section numbers (F-x.y) follow the spec where a feature came from it. Features added later have no number.

Conventions used below:

- Everything is scoped Organization → Workspace. Most models carry a `workspace` FK and use `WorkspaceScopedManager` (`apps/common/managers.py`).
- Workspace URLs are mounted under `/workspace/<workspace_id>/...` (see `config/urls.py`).
- Background work runs in the `process_tasks` worker (django-background-tasks; `apps/common/background.py`, `apps/common/worker.py`). There is no Celery or Redis requirement.
- Defaults referenced as `publishing.retry_max_attempts` etc. come from `apps/settings_manager/defaults.py` (`APP_DEFAULTS`), and can be overridden per org/workspace via `OrgSetting` / `WorkspaceSetting` rows. Those rows are edited in Django admin. The `/settings/` page is a static page with no editor.
- UI languages are Português (Brasil) and English (US) (`LANGUAGES` in `config/settings/base.py`). The language picker posts to `/i18n/`. Translation rules are in `.claude/skills/translation/SKILL.md`.

## 1. Organization, workspaces, members

### F-1.0 Account profile — `apps/accounts/`
- Account centre → Profile (`accounts:settings`): photo, first and last name, e-mail language (`User.language`: the language every e-mail to the person goes out in; set from the page they signed up on), postal address (CEP, street, number, complement, neighbourhood, city, UF) and password. `ProfileForm` (`apps/accounts/forms.py`) writes `User.name` from first + last name, normalises the CEP to `00000-000` and accepts the address only complete (complement is the one optional part) or empty. Accounts that predate first/last name are offered their `name` split. The data goes with the user when the account is deleted. It is not sent to Asaas yet. Typing the eighth digit of the CEP (masked as 00000-000 by the shared `data-mask="cep"`) fills street, neighbourhood, city and UF from ViaCEP through `accounts:cep_lookup` (`apps/accounts/address.py`, asked server-side because the page's CSP only lets scripts call this application); an unknown CEP or a failing lookup shows a hint and the fields stay open. The checkout's card form opens with the profile's CEP and number, and the ones typed there become the address of a profile that has none (`address.remember_address`; one the person wrote is never replaced), the rest filled from the CEP by the background task `accounts.tasks.complete_address_from_cep`. Nothing of the card itself is kept.

### F-1.1 Organizations — `apps/organizations/`
- `Organization`: name, logo URL, default timezone, billing email.
- A user may own or belong to several organizations (separate companies of the same person: each has its own brands, team, API keys and payer). The organization **in use** (`request.org`, resolved in `apps/members/middleware.py`) is the one of the workspace in the URL, else of the last workspace opened, else the first the user joined; `request.org_memberships` holds them all. The brand switcher lists the brands under each organization (`sidebar_org_groups` in `apps/common/context_processors.py`), which is how one moves between organizations; it only switches, and ends with "Manage organizations". Creating and editing live in one place, the account centre's "Organizations" page (`organizations:workspaces`): four totals at the top (organizations, people, brands, connected channels, counted only over organizations the user belongs to), a search and an order that work on the cards in the page, then one card per organization, those the user owns or administers first and newest first among them, with its name, a pill saying whose it is ("Your organization", "You are an admin", "You are a member"; the owner's name on the ones of someone else), creation date and its own numbers, "Edit" (the organization's own page, `organizations:manage`: its name and billing data in one form saved by `organizations:edit`, and for the owner the danger zone, which names every brand that deleting makes inaccessible and whether it is in use; only an owner or admin of that organization opens it) and "Create workspace" (the form sends `organization`; `workspaces:create` checks owner/admin of that one), and its brands underneath with Open and a three-dot menu (the brand's settings pages, Move, and for an owner or manager of the brand Archive, Restore and Delete, confirmed in a modal of the page and answered by `workspaces:settings`; the last brand in use of an organization is offered neither). An owner or admin sees every brand of the organization; any other member only the brands they were added to, and the organization's brand and channel numbers count just those; "Create organization" in the header (`organizations:create`, born with its first brand through `accounts.signals.create_organization_with_brand`, up to `MAX_OWNED_ORGANIZATIONS`). Organizations where the user is only a guest of a brand are listed last, without editing and without that brand's other members. The menu's team, API keys and billing links are about the organization in use; its name is shown on those pages, not in the menu. The invitation form (`members:invite`) picks the organization first, among those the user owns or administers, and then only that one's brands; an invitation into an organization other than the one in use answers with a toast instead of a row. Deleting an organization is in the danger zone of that page, also reached from "Delete organization" in the three-dot menu of its card, for its owner (scheduled for 14 days, or at once; asking for it e-mails the owner the day it goes and a link back to that danger zone, where the deletion is cancelled until then: `organizations/emails.py`, `organizations/email/deletion_scheduled.*`; `organizations:settings` is the same page for the organization in use and has no link). Deleting one's own account (`delete_account` on the profile) has no link or button in the interface; the handler remains.
- **Moving a brand to another organization** (`organizations:move_brand`, `workspaces.services.move_brand`; "Move" in the three-dot menu of a brand on Account centre → Organizations, which also holds the shortcuts to the brand's settings pages): for someone who is owner or admin of both organizations. Everything of the brand goes with it (posts, channels, inbox, automations, analytics, contacts, media, API keys, the people linked to it); custom roles of the organization it leaves are dropped from its members and that organization's pending invitations stop naming it. Billing follows the destination: a brand covered by the origin's plan gives its place back and the destination's plan covers it if it has a brand left; an exempt brand stays exempt, with its reason and end date; a brand charged on a gateway subscription of its own, or with extra disk contracted, is refused until that is cancelled, because the payer is the organization. Archived brands and destinations scheduled for deletion are refused.
- About your business (`organizations:about`, `organizations/about.html`): the first of three setup steps a new account goes through (Your company → Plan → Payment, `partials/_setup_steps.html`); the checkout sends the owner there while `organizations.views.needs_about` holds. The account counts as being set up (`organizations.views.needs_welcome`) while the organization has its sign-up name, or once it was named here until a brand is in use (paid, comped or on trial); meanwhile the checkout's "Your company" step links back to change the answers, and logging in leads back to the setup. Asks the activity (entrepreneur, freelancer, agency, marketing analyst — cards), team size and how they found us (selects; "somewhere else" opens an optional text field, `referral_source_other`) and the organization's name, asked after the activity picked (`Organization.name_question`: the agency's, the company's, the name a freelancer's clients know them by, or the employer's), which replaces the sign-up name; every question is answered, there is no skip. One more question follows the activity, on the same step (`Organization.extra_question`, required for that activity): how many clients an agency or freelancer serves, or the segment of a business or of an analyst's company. The answers live on `Organization` (`name`, `business_activity`, `team_size`, `referral_source`, `referral_source_other`, `about_answered_at`, `client_count`, `business_segment`; `goals` keeps what earlier accounts picked and is no longer asked) and show on the administrative Customers screen: the activity as a pill on the account row (and in its search), every answer in the account's "Edit account" panel. The three steps share the same head (`partials/_setup_header.html`: Moti, title, Log out), width, purple card headers and floating action bar (`.floating-bar`).
- Welcome step: an organization is created at sign-up as `Organization.DEFAULT_NAME`. While it is unnamed (`is_unnamed`), the owner's first screen (the contracting page, `billing/subscribe_modal.html`, which replaces base.html's `app_shell` like the sign-up page: logo and card only, no sidebar) asks, in steps, for the organization (name, CPF/CNPJ and phone, kept by `billing.services.set_payer_identity`) and then for the first brand's name (`organizations:welcome`), before showing the plan and the free trial. With the document and phone on file the trial starts with one click and contracting does not ask for the document again; "Create organization" asks for the same data. The dashboard sends an unnamed, not yet active account there even when unpaid brands are not locked.
- Account centre → Billing is about the organization in use: its brands only (plus brands the user manages in organizations they are a guest of), with the organization named at the top.
- Deleting one of several organizations keeps the owner's account and session; the account is deleted with the organization only when it was their last (`Organization.hard_delete`). The free trial is one per person: a user who owns an organization that had its trial gets none in another (`billing.services.trial_available`).
- The account centre menu has Profile, Organizations and Billing. API keys are managed in each brand's settings (`workspaces:api_keys`). The organization members page (`members:list`) has no menu entry: people are managed per brand, in the brand's Manage team page (`workspaces:team`). The organization's name is edited on the workspace list (`/organizations/workspaces/`, admins only), which also links the owner to the deletion page (`/organizations/settings/`, no longer in the menu and now only about deleting the organization).
- `default_timezone` is the fallback for workspaces without a timezone of their own and is no longer edited anywhere: the timezone is set per workspace (workspace settings, owner or manager, Brazil's timezones listed first). A new organization starts on `America/Sao_Paulo` (`apps/accounts/signals.SIGNUP_TIMEZONE`) unless the browser reports another at sign-up.
- Deletion: the owner requests it. That sets `deletion_requested_at` and schedules `execute_scheduled_org_deletion` (`apps/organizations/tasks.py`) for **14 days** later, and the deletion can be cancelled during that window. YouTube connections and copied YouTube API data are removed immediately when deletion is requested (`apps/social_accounts/youtube_compliance.py`). The owner gets an e-mail (`organizations.emails.send_deletion_scheduled`) that names the organization and its brands, the date, the YouTube channels already disconnected (only when there were any), the other networks that keep working and publishing until the date, and the link to cancel. After deletion the owner is redirected to `CUSTOM_SIGNUP_URL` if it is set. Every deletion (`Organization.hard_delete`, also used by the immediate deletion and by the operator's account deletion) first cancels the organization's Asaas subscriptions and add-ons (`contracting.cancel_organization_subscriptions`); if Asaas refuses, nothing is deleted.

### F-1.2 Workspaces — `apps/workspaces/`
- `Workspace`: name, icon, description, timezone, primary/secondary brand colour, default hashtags, default first comment, approval workflow mode, `is_archived`, `monthly_post_goal`.
- **Archived** (`is_archived`, set and cleared on the settings page): the workspace leaves the sidebar and the pickers and accepts no work until it is restored. Its pages answer 403 except the settings page (`RBACMiddleware.process_view`), its API keys are refused (`ApiKeyAuth.authenticate`), and the publisher sends nothing for it: a post that comes due while it is archived is marked failed with that reason and its author is notified (`PUBLISH_WORKSPACE_ARCHIVED_MESSAGE`), so it can be published again after the restore instead of going out late on its own. Posts due after the restore are untouched.
- **Deleting** a workspace (settings page) or an organization (`Organization.hard_delete`) also removes its stored files — asset files, thumbnails, version files and workspace icons: their names are read before the cascade (`media_library.services.tenant_stored_files`) and removed by the worker (`media_library.tasks.remove_stored_files`, queued in the same transaction; a storage failure is logged and the task retried). Member avatars belong to the user and stay.
- **Dashboard** (`/workspaces/<id>/dashboard/`, `views.workspace_dashboard`, numbers in `dashboard.py`): the home page (`/` sends the last used brand there) and the sidebar's "Dashboard". The header greets by the part of the day in the brand's timezone and sums up the day (`dashboard.day_summary`: posts going out today, pending approvals, unread messages, my tasks due today or overdue — each only for who can act on it; the approval and unread counts are `approvals.services.pending_approval_count` and `inbox.services.unread_count`, the same as the sidebar badges). Moti's hero card (`_ideas_hero.html`, tab `dashboard`); chips for what needs someone, each only for who can act on it (failed posts, pending approvals, unread inbox, accounts to reconnect) or "all caught up"; the reports page's area chart (`analytics/_hero_chart.html`) for one network at a time, chosen by pills (`?account=`) — reach is unique people, so networks are never added up; the monthly goal card; one card per connected network with up to three numbers chosen from what that platform reports (`dashboard.network_card`: the audience total when the platform has one, its primary metric, then the engagement rate or, without one, its next metrics — subscribers, views and watch time on YouTube; impressions and clicks on Google Business); "My tasks" (open tasks assigned to me, most urgent first, opening on the board with `?task=`; not for clients) and "Upcoming dates" (the brand's events and special dates of the next 90 days, `dashboard.upcoming_dates_with_posts`; special dates come even when the calendar grid hides them, and when nothing falls in those 90 days the brand's next three special dates of the year show; "Post ready" beside the day when an approved, scheduled or published post falls on it; the name and "See more" open the special-dates page with that date picked, `?date=<key>&day=<iso>`, or the page as it is for the brand's own events, which it doesn't list; shown only with `create_posts`); the network's four best posts; and "what works best" (`analytics.services.post_performance`: average engagement rate per format, and the best weekday and 3-hour block once there are 6 rated posts). `?range=7|30|90` sets the period, or `?start=&end=` the dates picked under "Custom" (see "Report periods" below). Analytics parts need `view_analytics`.
- **Monthly goal**: owners and managers set it on the goal card ("Set goal" / pencil → `dashboard_goal`, 1–999, empty removes it). Posts count once whatever the number of networks: published this month, plus scheduled for the rest of the month, against the goal, with a pace note (reached, covered by the schedule, on track, behind).
- Create, list and settings pages. The General settings page holds the brand's identity (logo, name) and preferences (timezone, segments); the approval flow has its own page in the brand's settings menu, `/workspaces/<id>/settings/approvals/` (`workspaces:approvals_settings`), which everyone in the brand sees and owners and managers change.
- Cross-workspace calendar at `/organizations/calendar/` (`apps/organizations/views.py`).
- A workspace can connect at most `MAX_ACCOUNTS_PER_PLATFORM` (default **1**) account per platform (`apps/social_accounts/views.py`). Reconnecting an account that already exists is always allowed.

### F-1.3 Members & RBAC — `apps/members/`
- Org roles: Owner, Admin, Member (`OrgMembership`). Org-level permissions are `manage_intelligence_billing`, `use_intelligence` and `manage_api_keys`.
- Workspace roles: Owner, Manager, Editor, Contributor, Client, Viewer (`WorkspaceMembership`). The permission keys in `PERMISSION_KEYS` are create/edit-others/approve/publish-directly posts, manage social accounts, view analytics, use inbox, reply from inbox, manage workspace settings, and upload/edit/delete/manage media. The role-to-permission map is `BUILTIN_ROLE_PERMISSIONS`.
- **Roles and permissions per organization** (`organizations:role_permissions`, the organization's three-dot menu on Account centre → Organizations; owners and admins of that organization): a table of permission × role that turns each permission on or off for Manager, Editor, Contributor, Client and Viewer in every brand of the organization. Stored as the differences from `BUILTIN_ROLE_PERMISSIONS` in `Organization.role_permissions` (`members.services.set_role_permissions` / `role_permission_matrix`) and applied by `WorkspaceMembership.effective_permissions`, so every check (views, API, MCP, API keys) follows it. The Owner role is never adjusted. Checks made on the role itself (owner-or-manager on the brand's settings and team pages) are not affected.
- `CustomRole` exists and is honoured by permission checks (`effective_permissions`), but custom roles can only be created and assigned in Django admin.
- Invitations (`Invitation`): invite, resend, revoke, accept-by-token. Invites expire after 7 days (`org.invitation_expiry_days`) and are single-use even if two signups use them at the same time. Per-member workspace assignment is at `members/<id>/workspaces/`.
- Enforcement: `apps/members/decorators.py` (`require_permission`, `require_org_permission`) and `apps/members/middleware.py`.

### F-1.4 Client portal — `apps/client_portal/`
- Clients are `WorkspaceMembership` rows with the Client role. They are invited from workspace settings → Clients (`urls_admin.py`).
- Access is passwordless: a magic link (`MagicLinkToken`, stored only as a hash) is valid for 30 days and single use, and the expired-link page lets the client ask for a new one. Redeeming it opens a session confined to `/portal/` (`apps/client_portal/middleware.py`): the client cannot reach workspace screens or other organizations with it until they sign out and sign in normally.
- Portal pages under `/portal/`: dashboard, approval queue (approve / request changes / reject / **request hold**), published posts, activity. `/portal/reports/` is a placeholder page. Every portal request needs a membership that still grants `approve_posts` (`portal_auth_required`), so a role change ends an open portal session.

### F-1.5 Platform API credentials — `apps/credentials/`
- `PlatformCredential` stores encrypted per-org app credentials for each platform and is edited in Django admin.
- `resolve_platform_credentials()` uses `.env` values (`PLATFORM_*`) when they cover all the keys a platform requires, and falls back to the org's admin-entered row otherwise. The connect page only offers platforms that have credentials configured.

### F-1.6 Configurable defaults — `apps/settings_manager/`
- The three-level lookup (app default → org → workspace) is in `helpers.py`. The keys in use include approval reminder hours, first-comment delay (120 s), retry attempts/backoff (3, at 1/5/30 min), inbox SLA target, notification quiet hours/digest, and client connection-link expiry.

### F-1.7 Client onboarding — `apps/onboarding/`
- **Connection links** (`ConnectionLink`): a manager creates a tokenised link with an expiry of 1 to 90 days (default 7), sends it by email, and can revoke it. The client opens a public page with no login, connects accounts through OAuth (or Bluesky/Mastodon forms), and the accounts land in the workspace. Each connection is recorded in `ConnectionLinkUsage`; the client's "Done" sends a `client_connected_accounts` notification to the workspace's owners and managers, only while the link is active and once until it connects more accounts. The Mastodon form refuses private and reserved addresses (`is_safe_url`), as the signed-in one does.
- **Get Started checklist** (`checklist.py`, `onboarding/partials/_checklist.html`, `checklist_partial` / `dismiss_checklist`, `OnboardingChecklist`): connect accounts, create first post, create first idea, invite team. Not shown anywhere: `base.html` does not include it and its context processor is not registered. The code stays to be placed on another screen.

## 2. Content creation & publishing

### F-2.1 Composer — `apps/composer/`
- Model: `Post` holds the shared content (title, caption, first comment, internal notes, tags, category, schedule). Internal notes have no field in the composer: they are written and read through the API and MCP, and saving in the composer keeps them. It has one `PlatformPost` per target **account and format** (`PlatformPost.format`: `default`, `story`, `reel`, `profile_photo`; unique on post + account + format), so one post can go out as an Instagram feed post and an Instagram Story at once, each with its own status, platform id, retries and metrics. A row can override title, caption, media and first comment and carries platform-specific options in `platform_extra`. **Status lives on `PlatformPost`.** The `Post` status is derived from its children (`apps/composer/status.py`).
- `PlatformPost.Status`: draft, pending_review, pending_client, approved, changes_requested, rejected, scheduled, publishing, published, failed, on_hold.
- Post types (`providers/types.py`): text, image, video, carousel, story, reel, link, article, poll, pin, short, profile_photo. A `story`, `reel` or `profile_photo` row publishes as that type (`FORMAT_POST_TYPES`); a `default` row's type is resolved from the media actually attached.
- Where to publish: the composer shows one card per connected account, with a toggle per format (`SocialAccount.format_options`, formats declared in `PLATFORM_FIELD_CONFIG["formats"]`): Feed / Story / Reels on Facebook and Instagram, post / photo on Google Business, and the ordinary post for every other platform. A count of the chosen destinations and "Clear" sit above the row. The channels on offer but not connected yet (`PlatformVisibility.unconnected_choices`, chat-only platforms excluded) become a single dashed "Connect channel" card. That card is shown only while the brand has no connected account. Once media is attached, a format it can't satisfy is greyed out with the reason. The cards are drawn by `templates/partials/_target_card.html`, shared with the art request's network picker (there the whole card is the network tab). The form posts `selected_targets` (`"<account>:<format>,..."`) next to `selected_accounts`. Formats can be picked before any media is attached; the composer warns when the media doesn't fit, and scheduling is refused (`format_blocker`, also checked by `publish_blocker` in the publisher): a Story needs at least one photo or video, a Reel one video, a profile photo one image. Instagram Feed + Reels on a single video is refused because both would publish the same Reel.
- Customize: one "Customize <channel>" chip per chosen format ("Customize Facebook Stories"), labelled by channel since a workspace has one account per platform. Each carries that format's own caption/title (`override_caption_<account>_<format>`, read by `_target_field`) and its options: the notify toggle for a Story, the gallery category for a Google Business photo, place and feeling for Facebook (account-wide, in the card of the first of feed/Reels chosen; each field is on screen only where the live API takes it — `providers/meta_feed_extras.py` has the table: place and feeling on a feed post without video, place alone on a Reel, sent on the finish phase and dropped on a refusal, neither on a feed video or a Story), and collaborators (up to 3), tagged people and location for Instagram (in the card of the account's first chosen format; account-wide, stored on every Instagram row; `providers/meta_feed_extras.apply_instagram_extras` sends each only where Instagram takes it: collaborators and location on a Feed image, the carousel parent and Reels, tags on the photo, the first photo of a carousel, Reels and Stories, with a position on photos only); while Stories is the only Instagram format chosen, the card offers the tags alone. With Reels chosen, the same card offers the Reel's cover as a moment of the video (the frame picker shared with TikTok, `composer/partials/_video_cover_picker.html`, sent as `thumb_offset`) and whether the Reel also shows on the profile grid (`share_to_feed`). The place picker (`composer/partials/_place_picker.html`, `compose/facebook-places/<account>/`) searches Meta's location Pages; Meta only answers it once the app has the Page Public Metadata Access feature, and until then the picker shows that reason. A chip turns amber when the attached media can't go out in that format.
- A Facebook feed post takes up to 15 photos (`FACEBOOK_MAX_ATTACHED_MEDIA`, exposed as `SocialProvider.max_images_per_post`). The limit is ours: Meta's `attached_media` took 50 when measured, and there is no album to overflow into (`POST /{page-id}/albums` answers `(#3) Application does not have the capability`). `composer.services.image_count_blocker` stops a larger post before it is scheduled — in the composer save, in `create_post` (API/MCP), in `require_publishable` and again in the publisher. Stories are not limited: several photos publish one by one.
- Stories are published without caption or first comment and get no comment automation; Facebook Stories go through `/photo_stories` and `/video_stories`. Meta takes one photo or video per Story, so a Story row with several media goes out as one Story per item, in order (`PublishEngine._publish_story_sequence`). Each live Story's id is saved on the row (`platform_extra["story_progress"]`, keyed to the row so a clone starts over) as soon as it is out; a retry resumes after the last one, and a failure part-way tells the user how many already went out.
- Notified Stories: "Notify me to publish the Story by hand" stores `platform_extra["delivery"] = "notify"` on the Story row. At the scheduled time the publisher does not call the platform (`apps/publisher/manual_delivery.py`): it notifies the author (or, without one, the members who can create posts) in-app and by e-mail with a link to `compose/<post>/manual/<platform_post>/`, a mobile page with the media to download, the caption to copy and an "I've published it" button. The row is settled as `published` with `notified_at` and is shown as "Notified"; it has no platform id, so no metrics, first comment or automation.
- Google Business photo: the `profile_photo` row adds the image to the profile gallery (v4 `media.create`, category stored as `platform_extra["photo_category"]`) instead of creating a local post. The v4 endpoints only route `accounts/{a}/locations/{l}`, so the provider resolves the owning account from the stored `locations/{l}`.
- Formats of one account share its queue slot (`apps/calendar/services._platform_post_for` / `_write_slot`); the slot is freed only when none of them is still scheduled (`drop_queue_entry_unless_scheduled`). Lists and calendar chips tag non-default rows with `templates/partials/_format_badge.html`; deleting from the list removes one format (`post_delete?platform_post=`).
- **Schedule**: the composer's "Schedule" button opens the date and time straight away: an inline calendar (flatpickr, in the page's language) prefilled with the calendar day the post was started on (`?scheduled_date=`; the time defaults to noon, `composer.views.DEFAULT_POST_TIME`), and a 24-hour time field that takes typing (14:30, 1430, 9) or a pick from a list of quarter hours. "Set Schedule" posts `action=schedule`, which the server refuses without a future date and time. The queue actions (`add_to_queue`, `add_to_queue_priority`) are no longer offered in the composer; the endpoint still accepts them.
- Live per-platform preview (`compose/preview/`): one tab per account (the arrows in the panel header step through them) showing that account's card, and a carousel with one slide per chosen format (format tabs above the card, dots below it) (Feed / Story / Reels, Google post / photo), each following that format's caption override. Ordinary posts render through `composer/partials/_preview_post.html` (the Facebook one as a feed grid); Story, Reels and the Google photo through `_preview_vertical.html`.
- Media: the "Add" tile, always last in the row, opens the media library (pick several at once, or upload from it); files dropped on the tile upload straight away. Import from Unsplash (needs `UNSPLASH_ACCESS_KEY`). Each thumbnail has a move handle (drag to reorder) and a settings button whose menu deletes or crops. ### F-2.2 Approval workflow — `apps/approvals/`
- Workspace mode (`Workspace.ApprovalWorkflowMode`): none, optional, required internal, or required internal + client.
- Actions: submit, approve, request changes, reject, resubmit, resume, and hold (from the client). They apply to the whole post or to a single `PlatformPost`, and every action is logged in `ApprovalAction`. A bulk action endpoint exists.
- Threaded comments (`PostComment`) with internal or external visibility, edit/delete (soft-deleted with `deleted_at`), @mentions (which send a `comment_mention` notification), and attachments served through a permission-checked view.
- Reminders and escalation (`tasks.py`): internal reviewers after 24 h, clients after 48 h, at most 2 reminders per post, then a stalled-approval escalation.

### F-2.4 Publishing engine — `apps/publisher/engine.py`
- `PublishEngine.poll_and_publish` finds due `scheduled` PlatformPosts, moves them to `publishing`, and dispatches them in parallel. Concurrency is bounded per post, per platform and globally (`infra.max_concurrent_publish_jobs`), and publishing capacity is reserved in the shared worker.
- Retries use exponential backoff (default 3 attempts). Non-retryable errors fail at once with a readable message (`apps/social_accounts/error_messages.py`), and a `post_failed` notification is sent.
- Publish confirmation: posts that publish asynchronously (for example video processing) are polled until confirmed, and the engine gives up on stale ones (`confirm_pending_publishes`).
- After a publish confirms, the engine posts the first comment (2-minute delay by default) and arms any comment automation attached to the post.
- `PublishLog` keeps a publish audit log for 90 days, and `RateLimitState` tracks per-account upstream rate limits.
- `apps/common/quota.py` is a shared circuit breaker for platform quotas, mainly for YouTube's per-client Data API budget.
- Posts that can only fail are refused at schedule time.

## 3. Inbox & engagement

### F-3.1 Unified inbox — `apps/inbox/`
- `InboxMessage` types: comment, mention, tag, DM, review. Statuses: unread, open, resolved, archived.
- Instagram mentions and tags (Facebook Login connection): the `mentions` webhook names a mention only by id, so it is filed with a placeholder and `fill_instagram_mention` (a background task) replaces it with the text, author and link read through `mentioned_comment` / `mentioned_media`. A reply to a mention goes through the account's `/mentions` edge, since the media is another account's. Posts that tag the account in the photo have no webhook: the poll reads the `/tags` edge and files them as `tag`, shown without a reply box because Meta lets no one answer them.
- Messages arrive two ways:
  - Webhooks at `/webhooks/facebook/`, `/webhooks/instagram_login/`, `/webhooks/whatsapp/`, `/webhooks/threads/` and `/webhooks/youtube/`. Meta requests are signature-checked.
  - The polling sync engine (`tasks.py` `InboxSyncEngine`, every 5 min by default), with historical backfill. YouTube polling uses bounded, resumable history walks to save quota.
- **Threads replies** arrive two ways, filed as comments on the post they answer through one mapping (`providers.threads.inbox_reply`), so the same reply is stored once. The `replies` webhook (`/webhooks/threads/`, `webhooks.threads_webhook`) shows it at once, but Meta delivers it only to apps whose Threads permissions have advanced access and never for a private profile's posts. So the poll stays: Threads has no feed of "replies to me", and each cycle reads the profile's latest posts and the conversation under each (`ThreadsProvider.get_messages`, `REPLY_POSTS_PER_POLL`). Answering a reply publishes one under it (`reply_to_comment`). Reading needs the `threads_read_replies` permission, so a profile connected before it was requested has to reconnect.
- Replies follow a draft → send lifecycle (`InboxReply`: draft / sent / failed). The inbox UI, the REST API and MCP all go through the same layer (`services.py`).
- **DMs** (Facebook Messenger, Instagram via Facebook Login, Instagram Direct, WhatsApp Cloud API). WhatsApp is connected on the Social Accounts page through Meta's Embedded Signup and is a messaging-only channel: it never appears in the composer, calendar, analytics or automations. The account cards of the chat channels show whether private messages are reaching the inbox ("Messages active" / "Messages unavailable"). Send eligibility is in `reply_policy.py`, which enforces Meta's messaging windows: a standard reply within 24 h of the customer's last message, and a human-agent reply up to 7 days. Outside those windows sending is blocked with a reason (translated), which the inbox shows in place of the reply box, with a lock. Instagram DM OAuth scopes are controlled by `PLATFORM_INSTAGRAM_FACEBOOK_DM_SCOPES_ENABLED` (on by default).
- Assignment, internal notes (`InternalNote`), saved replies (`SavedReply`), bulk actions, and auto-resolve on reply.
- One inbox for every channel (the sidebar has no per-channel shortcut; WhatsApp is one of the platform filters). The page (`templates/inbox/feed.html`) fills the area beside the sidebar like the flow builder, without cards: a top bar with the title and the inbox's sections (`_inbox_tabs.html`: Conversations — this page —, Funnel — `apps/funnels` — and Contacts) (saved replies open from the reply box's "+"), a filter row (`_filter_bar.html`: the calendar's channel pills — "All" and one per connected platform —, tabs for direct messages ("Inbox"), comments and mentions with their unread count under the channel (a second click shows every type again), and search), then three columns split by rules: the entries — one per conversation (`inbox_services.thread_key`: the same person, account and kind, and for comments the same post; direct messages, comments and mentions stay apart), showing its latest message, how many messages it holds, whether any is unread and the origin of its post (Feed / Story / Reels: `InboxMessage.origin`, from the Connekt Flow post or `extra["post_origin"]`, which the Instagram comment poll and the first read of a post's preview record) — with their count and sort (newest / oldest), the conversation (`_message_panel.html`: the post it hangs off, the messages, the reply box with the first saved replies as shortcuts) and, from 2xl, "Entry details" (`_message_details.html`: channel, type, origin, post, status, sentiment, assignee, "Mark as resolved"); below 2xl status and assignee move to the conversation header. Opening an entry shows the whole conversation and reads it, as a WhatsApp-style chat (`views._chat`, `_chat_incoming.html`, `_reply_item.html`, `_note_item.html`): day separators, the customer on the left in white, the team's replies on the right with who sent them, internal notes on the right in amber, the time (workspace clock) inside each bubble, opened at the latest message; status, assignee and bulk actions apply to the whole conversation. The post a comment hangs off (`inbox_services.post_preview`: caption, image, link and origin Feed / Story / Reels) is read locally for posts published through Connekt Flow and otherwise from the platform (`get_post_preview` on the Instagram and Facebook providers), cached for 6 hours; a refused read says so on the entry. A tag or mention shows the other account's post from what the sync recorded (the Instagram `/tags` poll stores its picture and kind in `extra["post_image"]` / `extra["post_origin"]`, refreshed every cycle as the CDN links expire). The post card opens the chat, on the chat's background, and the person's later messages follow it.
- **The open conversation is live**: its bubbles (`partials/_thread.html`) poll `inbox:message_thread` every 4 seconds with the token they were drawn with (`services.thread_version`: the conversation's messages and replies) and are redrawn only when it moved, so a new message, a colleague's reply or the customer's reaction shows without a reload. Only the bubbles are replaced, never the reply box, so the text being typed stays; what the person wrote after the open entry is included in the redraw.
- **Sending a reply**: the platform answers inside the request, so the reply box (`static/js/inbox-reply.js`) empties at once and the text shows in the chat as a "Sending…" bubble (`_message_panel.html`, `inbox-sending` / `inbox-sent` window events) until the answer arrives. The form drops a second submit while one is in flight (`hx-sync`), and a refusal puts the text back in the box. Dates in the conversation header and in the list use the workspace's clock, like the bubbles.
- **Message options in a WhatsApp chat** (`services.supports_message_actions`): each customer bubble has a menu to react with an emoji (`inbox:react_message` → `services.react_to_message`, the six in `REACTION_EMOJI`, recorded in `InboxMessage.extra["team_reaction"]`; clicking the badge takes it off), to reply quoting that message, and to copy its text. A reply is a plain message unless the person picks one to quote: the composer sends its id as `quote`, `services.quote_for` accepts it only from the same conversation and keeps a snapshot in `InboxReply.extra["quote"]`, shown on top of the sent bubble. A reaction the customer puts on one of our replies arrives by webhook and is shown under it (`InboxReply.extra["customer_reaction"]`). WhatsApp has no API to edit or delete a sent message, so the menu has neither.
- The list refreshes itself within seconds when a message arrives (`inbox:version` poll). The reply box has an emoji picker (the composer's catalogue, `static/js/emoji-picker.js`), searchable saved replies with their variables filled in, an "insert name" button, Enter to send / Shift+Enter for a new line, a per-platform character counter, and the time the reply window closes (`static/js/inbox-reply.js`).
- Sentiment: a keyword-based classifier (`sentiment.py`) labels messages positive / neutral / negative, and a user can override it manually.
- SLA (`InboxSLAConfig`): a response-time target per workspace, with an `inbox_sla_overdue` notification.

### Funnels — `apps/funnels/`
- A workspace has funnels (`Funnel`), each an ordered list of stages (`FunnelStage`: name, colour, kind open / won / lost). The main funnel ("Vendas - Principal", with Novo lead, Qualificação, Proposta, Negociação and Convertido) is created on first use (`services.funnels_for`); its names are written in the language of whoever opens it first.
- An inbox conversation (the inbox's `thread_key`) sits in at most one funnel as an `Opportunity` (stage, value, interest, tags, notes, the person's name). A conversation with no opportunity counts as the first stage of the main funnel, so no row is written until someone moves or edits it (`services.ensure_opportunity`). Moves are recorded as `OpportunityActivity`.
- **Grouped by post.** Beside the sort, "Group: By person / By post" (`views._list_group`, kept in the session; not on the funnel screen). By post, comments come one entry per post (`inbox_services.with_thread_key(by_post=True)`, `_post_row.html`: picture and caption from Connekt Flow or the post-preview cache, never a platform read, the comment count and unread count, the latest comment), while direct messages and mentions stay per person. Opening a post (`inbox:post_comments`, `_post_panel.html`) shows it on top and its comments newest first, 50 at a time with "Load more", filtered by all / unread / unanswered (no sent reply) and a search; the comments drawn are read, the rest keep their status, and each one opens its conversation, which links back with "All comments on the post".
- The inbox's "Funnel" section (`funnels:inbox`) is the inbox page (`inbox.views.feed_context` with a funnel scope) with a funnel bar (active funnel, stages with their count, "See the whole funnel"), each entry's stage, and "Opportunity details" in place of "Entry details" (`_opportunity_details.html`, opened with `mode=funnel`, which the panel passes on through an inherited `hx-vals`): contact (linked to Contacts when matched), funnel, stage, status, assignee, tags, interest, potential value, notes, "Move to <next stage>". Its composer has an "Automation" tab that runs the post's flow for a comment (`automations.actions.start_flow_for_message`: the same 7-day window, claim and log as an automatic run).
- The board (`funnels:board`): figures (conversations, active opportunities, converted, conversion rate, potential value), filters (funnel, channel, assignee, tag, origin, search, period), one column per stage with its count and value, cards dragged between stages (`funnels:board_move`), "Add opportunity" (conversations not in the funnel yet), funnel performance and recent activity.
- Settings (`funnels:settings`, `manage_workspace_settings`): create and rename funnels, add, edit, reorder and delete stages. Deleting a stage moves its conversations to the funnel's first stage; deleting a funnel sends them back to the main funnel; the main funnel cannot be deleted.

### Automations (comment-to-reply / comment-to-DM) — `apps/automations/`
Not in the original spec. It is adapted from BrightBean Chat and runs on **Facebook, Instagram and Instagram Direct** comments only (`matching.COMMENT_PLATFORMS`). In the "new rule" chooser, Google Business is shown as "coming soon".

- **Rules** (`AutomationRule`) belong to one account, or to all compatible accounts when no account is set.
  - Matching: include/exclude keywords with five modes (`keywords.py`): exact, contains, any_word, and accent-insensitive contains_loose / any_word_loose. Rules can be scoped to all posts or to specific posts, and to top-level comments only.
  - Rules are evaluated in priority order and the first match wins (`matching.py`).
  - Replies: a public comment reply and/or a private reply (DM). Each uses a fixed text or a random variation. The `ai` mode is declared but inert.
  - Guards (`guards.py`): once per sender per post, `max_per_hour` (default 30), and the account's own comments are skipped. Every decision is logged in `AutomationLog`, with outcomes sent / skipped_* / no_match / failed.
  - New rules start disabled. A rule has a "test" action, and the log is at `automations/log/`.
- **Flow builder** (`flow_views.py`, `flow.py`, `engine.py`, `templates/automations/flow_builder.html`): a canvas of nodes and edges.
  - Node types: `trigger_comment`, `reply_comment`, `send_dm`, `send_card` (image card, picked from the media library), and `condition`. A condition branches on comment text or on the sender's profile: follows us, we follow them, verified, follower count.
  - Messages can carry buttons. A postback button parks the run in `FlowRun`, keyed by account and sender, until the person taps it.
  - Execution: `flow.py` compiles the canvas into the rule's fields. `engine.py` walks the graph, sends at most 5 messages per wake (`MAX_STEPS_PER_WAKE`), stops cycles, and abandons the run on the first send failure.
  - One private message until the person answers: Instagram and Facebook deliver a single private reply per comment, so a flow that would send a second one before a reply-button tap is saved but cannot be switched on (the editor says why), and the engine never attempts the second.
- **Per-post flows** (`PostAutomation`): a flow is bound one-to-one to a `PlatformPost`. If the post is still a draft or scheduled, the flow waits as `pending`. The publisher arms it (`services.arm_for_platform_post`) when the post is confirmed live, and on an already-published post it arms on save. Existing scheduled or published posts can be chosen from `flow_choose_posts`.
- **Flow templates** (`FlowTemplate`): a global library edited by staff at `/staff/flow-templates/` (create, edit canvas, details, thumbnail, duplicate, publish, reorder). Authors start a flow from a published template through `templates/`. The graph is copied, so later edits to the template do not reach flows already created from it.

### Contacts (not in spec) — `apps/contacts/`
People and companies the workspace talks to (sidebar: Engajar → Contatos, for members with `use_inbox`).

- **Where contacts come from:** created by hand (`contacts:create`), imported from a CSV with the export's columns (`contacts:import`; only `name` is required, a row whose WhatsApp, Instagram or email already belongs to a contact is skipped, 5,000 rows / 2 MB), or by the Inbox: the first message from a sender creates a `Contact` with a `ContactChannel` holding the sender's platform ID (`services.on_inbox_message_created`, from the same two places as the automations hook). A later message from the same person lands on the same contact through that ID, or through the channel's value when the person arrives under their @handle or was typed in by hand. A Facebook DM is a Messenger channel; a Facebook comment is a Facebook channel.
- **Engagement:** `interactions_90d` counts the inbox messages the contact sent in the last 90 days (matched through its channels, `services.interactions_queryset`); 5 or more is high, 2–4 medium, fewer low. A level chosen in the form (`engagement_manual`) wins. The daily `refresh_contacts` task creates contacts for senders the live hook missed (any date, so its first run imports the history), recounts recent senders and lets quiet contacts decay.
- **List** (`contacts:list`): cards (total, active, funnels in use, new in 30 days, engagement rate = share of high or medium), channel chips, search and filters (status, source, funnel, tag, segment, engagement, last contact) swapped over HTMX and kept in the URL, pagination, a floating selection bar (delete, and merge for two or more: the person picks the contact that stays, `services.merge_contacts` moves the others' channels with their inbox link, joins the tags, fills its empty fields, appends each other contact's notes whole under a "Merged from <name>" block that lists the values differing from the kept contact's (status, source, company…), and deletes them), an inline funnel select (`contacts:set_funnel`) and CSV export of the filtered list (cells that start like a formula are escaped).
- **Form:** personal data (CPF/CNPJ with check digits, date of birth, gender, company, photo up to 2 MB), channels (one is the main one), status, funnel, tags, segment, source, engagement and address; the edit page also lists the contact's Inbox interactions.
- **In the Inbox:** the open entry's details column shows the sender's contact (`services.contact_for_message`, read-only): source, tags, funnel, engagement, last contact and a "View profile" link.
- **One person across channels:** Meta gives no link between someone's Instagram and Messenger IDs, so the team joins them. The open conversation's header has "Merge contact" (`inbox/partials/_person_channels.html`): a dialog that suggests contacts whose name starts with the same first word, or searches like the list (`contacts:merge_candidates`, `services.merge_candidates`), where several can be ticked (they stay ticked across searches), and posts them to `contacts:merge` with the main contact the team picks in the same dialog (the one on screen by default), the one that stays. Each contact in the dialog shows how much data it holds (channels, interactions, filled fields, last contact) and the one with the strictly highest score is marked "Most complete" (`services.merge_summary`, `services.most_complete`). Conversations stay one per channel (each reply goes out through its own channel and window); once the contact talks through more than one, the header shows a chip per channel (`services.contact_conversations`: the latest message per account and type) that opens that channel's conversation, and the list shows the sender's other channels beside the name (`services.other_channels_by_message`, matched on the inbox ID).
- **Not built yet:** the Funnels, Lists, Segments and Campaigns tabs show as "Coming soon". Funnel and segment are free text on the contact (with suggestions from the values in use) until those tabs give them their own models.

## 4. Analytics — `apps/analytics/`

### F-4.1 Per-account and per-post analytics
- Snapshot tables: `AccountInsightsSnapshot` (daily account metrics), `PostInsightsSnapshot`, and `YouTubePeriodReport` (native YouTube reports, cache-only for display).
- A Threads profile is measured from the day it is connected, with or without posts published from here: profile views, likes, replies, reposts and the follower total (`ThreadsProvider.get_account_metrics`); "Import history" brings the posts published directly on Threads (`list_existing_posts`), which are then measured like any other, and the views of the days before.
- The metric catalog for each platform is in `metrics.py`. Engagement rate and period deltas are computed in `derive.py`, and values the product calculates itself are labelled as estimates.
- Pages: workspace overview (`index`), per account (KPI cards, trend charts over 7/30/90 days or custom dates, sortable post table with its own period, `table_range` / `table_start` / `table_end`), and post detail. All of them, and the sidebar's "Reports" link, need `view_analytics`.
- **Report periods** (`apps/common/periods.py`, tag `{% period_picker %}` in `common_extras`, `components/_period_picker.html`, `static/js/period-picker.js`): the period pills of the reports, the Shopee and Meta Ads reports, the brand dashboard and the Meta Ads pages. Besides the presets (`?range=`), "Custom" opens a range calendar (flatpickr) and sends `?start=&end=` (at most 365 days, ending no later than today; Shopee's no earlier than the days it reports). Every period is "N days ending on a date", so the comparison with the previous period stays the N days just before. Links and HTMX requests carry it as `period.query`; the picker keeps the page's other parameters. YouTube's stored period reports exist only for the presets: a custom period is derived from its daily series. The funnel board's period is a dropdown and has no custom dates.
- Sync cadence (`tasks.py`):
  - On connect: a backfill.
  - Account metrics: daily.
  - Post metrics: hourly for posts under 24 h old, every 6 h up to 7 days, daily up to 30 days, weekly up to 90 days, then no more syncing.
  - Days with no activity are stored as zeros. Days the platform did not report are drawn as gaps.
- Instagram analytics have their own access check, separate from Page publishing (`instagram_access.py`). Analytics are paused when a provider quota is hit (`ProviderQuotaBlock`).
- **Shopee Affiliates** (`shopee/<connection_id>/`, view `shopee_report`, numbers from `apps/radar/reports.py`): listed in the account switcher under "Affiliate sales", and the landing page when the workspace has no channel. Same layout: commission, orders, sales and items sold cards with deltas, commission per order with orders by status, the trend chart, top products, where sales came from (Shopee's `referrer`) and the orders table filtered by status. Read live from Shopee's `conversionReport` (cached 15 minutes, nothing stored); pending orders count, cancelled ones only as cancelled; days are the workspace's. Shopee only answers for the last 90 days, so the 90-day range has no comparison.

### History import (not in spec) — `history_import.py`
- From an account's analytics page (`<account_id>/history/`), the user can import posts the channel already had. The import uses `SocialProvider.list_existing_posts`. Imported posts become ordinary `PlatformPost` rows, marked in `platform_extra`, and the normal sync then collects their metrics.
- The account chart is also backfilled for the days before the connection, where Meta's API returns a daily series: Facebook page insights (all four metrics) and Instagram reach. Days the product already measured, and today, are never overwritten.

## 5. Platform configuration

### F-5.1 Authentication — `apps/accounts/`
- Email/password signup and login through django-allauth, Google SSO (`GOOGLE_AUTH_CLIENT_ID`), terms acceptance, and an account settings page. Sign-up asks the person's name first (`accounts.forms.SignupNameForm`, `ACCOUNT_SIGNUP_FORM_CLASS`; split into `first_name`, `last_name` and `name` as the profile keeps it; Google fills it from the profile), and the account e-mails greet by the first name (`User.greeting_name` through `ACCOUNT_USER_DISPLAY`: first name, else the start of the name, else the part of the address before the @). The password fields of log-in, sign-up and the new password have an eye that shows what is typed (`partials/_password_input.html`). A new account gets a welcome email; changing or resetting the password, changing or removing an email address and connecting a social login each send a security notice with the date, IP and browser and a "reset my password" button. Every email shares one layout (logo, card, legal footer; see `docs/architecture.md` §15). On a desktop the Google round trip runs in a popup, like the account connections: the button posts to allauth with `next=/accounts/popup-done/`, and that page (`views.login_popup_done`, rendering `social_accounts/connect_done.html`) tells the login page to carry on and closes the window. On touch devices, narrow screens or a blocked popup the page navigates as before.
- **E-mail verification** (mandatory, by code; `ACCOUNT_EMAIL_VERIFICATION*` in `config/settings/base.py`): after the sign-up form the account types the six digits sent to its address (`account/confirm_email_verification_code.html`, one box per digit, sent when the sixth is in), where it can also ask for a new code or correct the address. A new code replaces the one before, so one is sent at most every 60 seconds (`accounts.views_signup.VerificationCodeView`, `RESEND_COOLDOWN`): the page counts the wait down where the button will be and an earlier request sends nothing. One verification may ask for 5 new codes (`ACCOUNT_EMAIL_VERIFICATION_SUPPORTS_RESEND`); after that the page says to sign in again. Only then is it signed in, welcomed by e-mail (`accounts.signals.welcome_once_the_address_is_confirmed`) and sent to its setup steps, whatever `next` the sign-up carried (`AccountAdapter.post_login`). An unverified account that signs in is asked the same. Not asked: a Google sign-up (verified by Google), an invitee who signs up with the invited address, and a team account created by the team; they are welcomed at sign-up. Accounts that predate verification were marked verified by `accounts/0008`.
- `SIGNUP_MODE` = `open` | `invite` | `closed`. `CUSTOM_SIGNUP_URL` replaces every "Sign up" link and, in `invite` or `closed` mode, is where blocked signups are sent (`signup_links.py`, `adapters.py`).
- Auth POSTs, including the Django admin login, are rate-limited per IP: 10 attempts per 60 s (`apps/accounts/middleware.py`). Sessions last 14 days (`SESSION_COOKIE_AGE`).
- 2FA: the TOTP fields exist on `User`, but there is no setup or enforcement flow yet.
- **Operator impersonation** (`impersonation.py`, `views_impersonation.py`): staff can sign in as a customer for support. Staff cannot impersonate other staff. Start and stop are POST-only, and every session is recorded in `ImpersonationSession`, which can be viewed in the staff console. A takeover ends on its next request once the operator is deactivated or loses staff status (`ImpersonationGuardMiddleware`), and it can neither approve an OAuth client nor issue an API key. It cannot schedule or publish either: the attempt is refused with a message and the post stays as it was; nor can it delete or archive the organization, a brand or the account, pay or change the subscription, invite or change roles, change ads, reply from the inbox, send a client-portal or connection link, or change the account's e-mail, password or Google sign-in. Each refusal shows a message and changes nothing. Every page can still be viewed and settings adjusted, for diagnosis.

### F-5.2 Branding
- Per-workspace logo/icon and primary/secondary colours (`Workspace`), plus the organization logo URL. There is no custom domain or email white-labelling.

### F-5.3 Integrations
- Unsplash stock search and import in the composer.
- Outgoing webhooks are a notification channel (see F-7.1).
- The REST API and MCP server are described below. There are no other design, communication or storage integrations.

### Agent API — `apps/api/`, `apps/api_keys/`
- REST API built with Django Ninja at `/api/v1/`, with OpenAPI docs at `/api/v1/docs`. Routers: `me`, `accounts`, `posts` (create, get, patch, schedule, cancel), `media` (upload, get), `analytics` (account, post), `inbox` (list, get, reply drafts, send).
- **API keys** (`ApiKey`; requires the organization permission `manage_api_keys`). Managed per brand, in brand settings → API keys (`workspaces:api_keys`, `/workspaces/<id>/settings/api-keys/`, also in the brand's three-dot menu on the Organizations page): the page lists that brand's keys and issues a key for it, without a brand picker. The organization-wide list at `/organizations/api-keys/` (`api_keys:list`) still answers but has no menu entry; both are `api_keys.views.list_keys`, and the forms post `from_brand` so issue/edit/revoke return to the brand's page:
  - A key belongs to one workspace and has an explicit allowlist of social accounts and a subset of permission keys. On each request its permissions are intersected with the issuer's current permissions, so the key stops working if the issuer loses membership; it also stops while the issuer's account is deactivated.
  - The posts routes and MCP tools follow the composer's edit rules: changing, scheduling or cancelling a post written by someone other than the key's issuer needs `edit_others_posts`, and a PATCH that changes the title, caption, first comment or media of an approved post sends it back to `pending_review`.
  - Token format is `bb_studio_<secret>_<lookup>`. Only an HMAC hash of the secret is stored. Keys can have an expiry and can be revoked or edited.
  - `ApiKeyAuditLog` records audited actions.
- Limits (`limits.py`): per-key, per-workspace and per-IP throttles; hourly and daily call caps counted in `ApiKeyUsageHourly`; and per-platform daily post caps per account (`PLATFORM_DAILY_POST_LIMIT`, e.g. Instagram 25, TikTok 15, Threads 250). Writes accept idempotency keys (`IdempotencyRecord`).

### MCP server — `apps/mcp/`
- Streamable HTTP MCP endpoint (POST only, tools only) at `/api/v1/mcp`. It accepts the same bearer API keys, or OAuth tokens (below). An OAuth caller acts with their own role in the workspace they last opened (`User.last_workspace_id`); `list_accounts` names that workspace. Accepting an invitation does not change it while the user still has a workspace in use. A deactivated user's tokens are refused.
- 20 tools (`handlers.py`):
  - Posts: list_accounts, create_draft, schedule_post, schedule_draft, get_post, list_posts, cancel_post.
  - Media: search_media, get_media, upload_media, request_media_upload, finalize_media_upload.
  - Analytics: get_account_analytics, get_post_analytics.
  - Inbox: list_inbox_messages, get_inbox_message, create_reply_draft, update_reply_draft, discard_reply_draft, send_reply.

### OAuth server for MCP clients — `apps/oauth_server/`
- An OAuth 2.1 authorization server (django-oauth-toolkit) so MCP clients such as Claude Desktop can sign users in directly. Endpoints: `/oauth/authorize/`, `/oauth/token/`, `/oauth/revoke_token/`.
- Open Dynamic Client Registration (`/oauth/register`, RFC 7591, rate-limited), with metadata documents under `/.well-known/`.
- PKCE is required and only `S256` is accepted (`validator.py`).
- Changing or resetting the account password revokes every OAuth token of that user (`services.revoke_user_tokens`); the clients have to be authorized again. API keys are not affected.

### Intelligence — `apps/intelligence/`
- An optional integration with the separate BrightBean Intelligence service (third-party, run by upstream). It is enabled only when `INTELLIGENCE_INTERNAL_URL`, `INTELLIGENCE_PUBLIC_URL` and the related secrets are set, otherwise every Intelligence surface is hidden.
- Org-scoped at `/orgs/<org_id>/intelligence/`.
  - Subscription: plan picker, checkout through Intelligence (Stripe), recovery after a closed tab, portal, billing contact. State is kept in `IntelligenceSubscription`, `StudioCheckoutAttempt` and `PendingActivation`.
  - Tools playground: score packaging, score video hook, benchmark channel or video, research content gaps, list niches.
- Calls go through `services/client.py`, which signs internal calls with HMAC and uses a bearer key per org for tool calls. Using the tools needs `use_intelligence` and an active subscription. The Intelligence plan also sets the org storage tier (`STORAGE_QUOTA_TIERS`).

## 6. Media library — `apps/media_library/`

### F-6.1
- Workspace libraries (`/workspace/<id>/media/`) and a shared org library (`/organizations/media/shared/`).
- Nested folders, tags with autocomplete, starring, search, move, download, and alt text, title and attribution fields.
- The library page (`library_index.html`) has the standard page header with "New folder" and "Upload"; the folder column also creates folders, and the grid is titled with the open folder. Folder errors (blank or duplicate name) come back as an error toast. Files (not the organisation's shared ones) can be ticked on the grid or the list; a floating bar then counts them and offers "Move" (a window listing the brand's folders, or "No folder") and "Delete" (`asset_bulk_move` / `asset_bulk_delete`, gated by `edit_media` / `delete_media`; a file a scheduled post still uses is kept and the toast says how many). The media picker (`composer/partials/_media_picker_modal.html` + `media_picker.html`) is drawn the same way: "New folder" and "Upload" in its header, the folders column the whole height with "Folders" and its "+" on top, the toolbar over the grid only, and each file being uploaded listed above the grid until it is done or failed.

## Affiliates (not in spec) — `apps/affiliates/`

## Operational and compliance

- Public legal pages for Meta App Review (`apps/common/legal_views.py`): `/exclusao-de-dados/` (also `/data-deletion/`) explains how to delete data, shows the status of a platform's deletion request and receives Meta's deletion callback. The Privacy Policy and the Terms live on the public site (`connektflow.com.br/privacidade/` and `/termos/`, repository `connektflow-site`); `/privacidade/`, `/termos/`, `/privacy/` and `/terms/` redirect there, and signup, terms acceptance and email footers link there. `/robots.txt` (same module) allows Meta's crawlers by name, which read these pages and the media of every post.
- YouTube compliance (`youtube_compliance.py`, `YouTubeRevocation`): handles grant revocation and the retention lifecycle of YouTube data.
- Field-level encryption of tokens and credentials (`apps/common/encryption.py`, keyed by `ENCRYPTION_KEY_SALT`).
- `/health/` endpoint. Stale task locks are released when the worker starts.
